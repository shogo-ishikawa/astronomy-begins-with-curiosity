## 1. プロダクト概要

ABCsは、天文学の知識を前提としない学部生が、既知の宇宙の謎を題材に、実際の科学研究と同じ考え方と道筋を体験する教育用Webアプリである。

学生は、用意された手順を受動的にこなすのではなく、次の研究サイクルを自分の選択として進める。

> 宇宙への興味 → 研究可能な問い → 仮説と予想 → 研究計画 → 試し計算 → 計画修正 → データ取得 → 品質確認 → 解析 → 図 → 解釈 → ミニ論文 → 次の問い

研究パートナーのMiraが、専門用語や判断材料を丁寧に説明し、学生が自分で考えられる範囲を広げる。Miraは答えを代行する先生ではなく、「少し先を歩く共同研究者」である。

### 1.1 ブランド

- アプリ名: **ABCs — Astronomy Begins with Curiosity**
- 副題: **Undergraduate Astronomy Research Lab**
- 日本語タグライン: **宇宙への疑問を、研究のかたちに。**
- 研究パートナー: **Mira**
- Miraの一人称: **私**

### 1.2 v0.1の研究テーマ

- テーマ名: **宇宙の網目はどう育つ？**
- 大きな問い: **宇宙はどのように現在の姿へ進化したのか？**
- 研究可能な問い: **宇宙の時間とともに、物質密度のむらはどのように変化するか？**
- 方法: 宇宙論的N体シミュレーションの事前計算済み結果を用いる
- 主な観測量:
  - 投影密度分布
  - 密度コントラスト
  - 密度コントラストの標準偏差
  - 高密度領域の割合（補助）
- 発展解析: 二点相関関数

## 2. 目的と学習成果

### 2.1 プロダクト目的

1. 科学や学問の面白さ、宇宙を研究するワクワクを伝える。
2. 「何を知るために、なぜこのデータを、この方法で解析するのか」を考える体験を提供する。
3. 結果、解釈、結論、限界を区別する科学的思考を育てる。
4. 数学、物理、統計、情報、数値計算の授業内容が研究でどう使われるかを可視化する。
5. 一つの研究から新たな疑問が生まれる循環を体験させる。

### 2.2 対象者

- 主対象: 天文学の専門知識を持たない学部生
- 前提知識: 高校数学程度を想定するが、数式を読めなくても基本コースを完了できる
- Python: 未経験でも完了可能。希望者のみPython体験へ進める
- 利用形態: 個人での自習
- 基本端末: PC
- 目標時間:
  - 基本コース: 45〜60分
  - Python発展: 追加20〜30分

### 2.3 完了時に説明できること

学生は完了時に、少なくとも次を選択式の研究記録として説明できる。

1. 自分が何を知りたかったか。
2. どのような仮説と予想を立てたか。
3. なぜその箱サイズ、粒子数、snapshotを選んだか。
4. 試し計算から何を学び、計画をどう修正したか。
5. どのデータをどのように解析したか。
6. 図から直接分かったことは何か。
7. その結果をどう解釈したか。
8. 何がまだ明らかになっていないか。
9. 次に何を調べたいか。

### 2.4 非目標

v0.1では次を実装しない。

- 実際のCWSとの自動接続
- ライブのN体計算
- 撮像・分光・時系列観測コース
- FITSリダクション、測光、スペクトル線同定
- アカウント、ログイン、クラウド同期
- 教員用ダッシュボード、成績、ランキング
- 生成AIによるMiraの自由会話
- 英語版
- スマートフォンに最適化した全機能UI
- 完全自由なPython開発環境
- PWA、Service Worker、オフライン完全対応

## 3. 教育設計の原則

### 3.1 誘導はするが、一本道にはしない

- 主要な研究判断には複数の選択肢と結果を用意する。
- 選択肢は見た目だけでなく、計画評価、試し計算、図、解釈へ反映する。
- 取り返しのつかない行き止まりは作らない。
- 不適切な計画は、理由を理解して修正する経験へ変える。
- 修正前の研究計画も履歴として残す。

### 3.2 仮説はデータを見る前に正誤判定しない

- 「むらが成長する」「変わらない」「より一様になる」など、異なる仮説を選べる。
- Miraは仮説が問いに対応しているかを確認するが、正解を先に教えない。
- 結果を得た後に、予想と証拠を比較する。

### 3.3 研究設計と知識問題を区別する

- 知識問題には正誤がある。
- 研究設計には長所、短所、制約がある。
- 設計選択を「不正解」と呼ばず、「この問いには情報が不足する」「この計算資源では重い」など具体的に説明する。

### 3.4 「まだわからない」を常に許容する

- 研究判断の主要画面には、原則として「まだわからない」を用意する。
- 選択時にはMiraが追加説明、比較図、ヒントを提示する。
- 「まだわからない」を選んでも進捗や評価に不利益を与えない。

### 3.5 学生が研究の必須部分を選ぶ

次は自動決定してはならない。

- 興味を持った点
- 研究の問い
- 仮説と予想
- 研究で優先するもの
- 箱サイズ、粒子数、snapshot
- 試し計算で比較する項目
- 計画を維持・修正する判断と理由
- 主解析と図
- 図の説明
- 直接的な結果
- 解釈、結論、限界
- 次の研究の方向

### 3.6 自由記述は任意

- 初心者は選択肢だけで最後まで完了できる。
- 主要項目には任意の「自分の言葉で一文」を設ける。
- v0.1では自由記述を自動採点しない。

## 4. 共通体験部品

### 4.1 「研究への招待」

各テーマは、研究計画の前に必ず次の共通部品を持つ。

1. 心を引く問い
2. 現象を示す簡単な模式図またはアニメーション
3. 何が不思議なのか
4. 分かると何につながるのか
5. どの方法で調べるのか
6. 学生が今回行う研究
7. 「どこが気になったか」の選択

v0.1の模式図は、外部画像に依存せずSVGまたはCanvasで作る。初期のほぼ一様な分布と、現在の網目状分布を示す。ただし、後で学生が作る定量グラフを冒頭で見せない。

### 4.2 「この研究につながる授業」

用語解説とは別に、授業と研究をつなぐカードを設ける。カードは科目名だけでなく、現在の操作で何が使われているかを説明する。

最低限、次を実装する。

| 場面 | 学問とのつながり |
|---|---|
| 粒子の時間発展 | 解析学・力学: 微分方程式と数値積分 |
| 箱サイズと粒子数 | 数値計算: 分解能、計算量、メモリ |
| 密度コントラスト | 数学・物理: 平均からの相対的なずれ |
| 標準偏差 | 確率・統計: 分散と標準偏差 |
| ヒストグラム | データサイエンス: 分布の可視化 |
| 二点相関関数 | 統計・フーリエ解析: 空間的な相関 |
| 図と結論 | 科学的方法: 証拠と主張の対応 |

関連付けは科学的に正確な場合のみ表示し、無理に授業名へ結び付けない。

### 4.3 用語解説

- Miraの発言、本文、図のラベルに用語リンクを置く。
- PCでは右側パネル、狭い画面では下部シートに表示する。
- 1画面で初登場する新用語は原則2〜3個までとする。
- 用語項目は次を持つ。
  - 一言での説明
  - 今この場面で重要な理由
  - 図または具体例
  - もう少し詳しい説明
  - 関連する授業
  - 関連用語
- 本文への埋め込みは、例えば `[[density_contrast|密度コントラスト]]` のような一元的なマークアップからレンダリングする。

## 5. Mira仕様

### 5.1 役割

- 研究テーマの面白さを伝える案内役
- 学生の考えを問いによって引き出す共同研究者
- 専門用語と研究方法を説明する先輩
- 計画の矛盾や不足を一緒に見つけるレビュアー
- 迷いや失敗を研究の一部として支える伴走者

### 5.2 人格と口調

- 一人称は「私」。
- 丁寧な「です・ます」調。
- 親しみやすいが幼すぎない。
- 学生を見下さず、専門知識を前提にしない。
- 一度に一つの判断へ集中させる。
- 汎用的な称賛を連発しない。
- 何が前進したかを具体的に伝える。
- 「一緒に考えてみましょう」「ここから直接言えることは何でしょう？」などを用いる。

### 5.3 禁止する応答

- データを見る前に正しい仮説を教える。
- 研究設計を理由なく「正解」「不正解」と呼ぶ。
- 選択ごとに「すごい」「完璧」と褒める。
- 暗黒物質のみの計算から、星や銀河が直接形成されたと断定する。
- ノイズや数値誤差が完全になくなったと表現する。
- 根拠のない擬人化や感情的な圧力をかける。

### 5.4 視覚表現

- 人物イラストは使用しない。
- 変光星を想起させる抽象的な星のSVGを使用する。
- 通常サイズは40〜48px。
- 初回登場のみ大きく表示してよい。
- Miraの発言には星、名前、役割「研究パートナー」を表示する。
- 光の輪などで通常、考え中、注意、発見を区別できるが、色だけに依存しない。
- `prefers-reduced-motion` では明滅を停止する。

### 5.5 実装方式

- v0.1は生成AIを使用しない。
- コンテンツJSONと決定ルールから応答する。
- Miraの履歴をProjectStateへ保存する。
- 発言はステージ、選択、計画状態、解析結果、既読用語を条件に選ぶ。
- 同じ条件で同じ核心メッセージを返し、再現可能にする。

### 5.6 Python支援

Pythonを選んだ学生には、次の支援レベルを用意する。

1. 考え方のヒント
2. 次に必要な処理の説明
3. 関連する行の指摘
4. エラー内容の平易な説明
5. 修正候補
6. 動く完成例

学生はいつでも支援レベルを上げられる。支援利用にペナルティを設けない。

## 6. v0.1科学仕様

### 6.1 科学的に伝える中心内容

1. 初期宇宙の物質分布には小さなむらがあった。
2. 重力によって小さなむらが成長する。
3. 分布は一様な状態からフィラメント、ノード（ノット）、ボイドを持つ宇宙の大規模構造（コズミック・ウェブ）へ進化する。
4. 暗黒物質の高密度領域は、ガスが集まり天体形成が進みやすい重力場となる。
5. 暗黒物質のみのN体計算は、ガス冷却、星形成、フィードバックを直接計算しない。
6. したがって高密度領域を「銀河が形成された証拠」とは呼べない。

### 6.2 シミュレーション設定候補

CWSの基準設定を `Np=32^3`, `L=50 h^-1 Mpc` とする。

#### 箱サイズ

- `25 h^-1 Mpc`
- `50 h^-1 Mpc`（基準）
- `75 h^-1 Mpc`
- `100 h^-1 Mpc`

#### 粒子数

- `16^3 = 4,096`
- `32^3 = 32,768`（基準）
- `64^3 = 262,144`

#### 派生量

平均粒子間隔の目安:

```math
d_p = \frac{L}{N_{side}}
```

基準設定に対する粒子質量の比:

```math
\frac{m_p}{m_{p,default}}
=
\left(\frac{L}{50}\right)^3
\left(\frac{32}{N_{side}}\right)^3
```

基準設定に対する粒子データ量の目安:

```math
R_N = \left(\frac{N_{side}}{32}\right)^3
```

`L/Nside` は力の分解能そのものではないため、UIでは「粒子間隔の目安」と表記する。実際の力の分解能がメッシュやsofteningへ依存することを詳説に記載する。

### 6.3 設定評価軸

設定を次の四軸で表示する。

1. 大規模構造を含む体積
2. 小構造を表す粒子間隔・質量分解能
3. 計算負荷の目安
4. snapshot出力負荷の目安

単一の総合点は作らない。各軸と研究目的の対応を示す。

### 6.4 snapshot候補

結果パッケージは原則として次を持つ。

| ID | 赤方偏移 | 教育上の位置付け |
|---|---:|---|
| initial | `zStart` | ほぼ一様な初期状態 |
| z10 | 10 | 小さな密度のむらが成長し始める時代 |
| z5 | 5 | フィラメントや高密度領域が見え始める時代 |
| z2 | 2 | 宇宙の網目が明瞭になる時代 |
| z1 | 1 | 大質量構造や節がさらに成長する時代 |
| z0 | 0 | 現在に対応する分布 |

- `zStart` はデータパッケージの実値を使用する。
- 宇宙の晴れ上がりは観測的背景として示し、N体計算のsnapshotとして扱わない。
- `z=10` を「初代銀河そのものを計算した」と表現しない。「初期銀河が存在する宇宙史上の時代に対応する暗黒物質分布」と説明する。

### 6.5 snapshot選択ルール

- 学生はsnapshotを自分で選ぶ。
- 研究実行可能判定には次を推奨条件とする。
  - initialを含む
  - z=0を含む
  - 中間時刻を2個以上含む
  - 合計4個以上
- 条件不足でも即座に選択を強制変更せず、Miraが何を答えられなくなるかを説明する。
- 完成計画では推奨条件を満たす必要がある。

### 6.6 基本統計量

密度コントラスト:

```math
\delta = \frac{\rho - \bar{\rho}}{\bar{\rho}}
```

密度コントラストの標準偏差:

```math
\sigma_\delta = \sqrt{\langle\delta^2\rangle}
```

高密度領域の割合（補助）:

- 初期値は `rho / mean(rho) > 5` とする。
- 閾値は学生が変更できる。
- グリッド分解能と平滑化に依存することを限界として示す。

二点相関関数（発展）:

```math
\xi(r) = \langle\delta(x)\delta(x+r)\rangle
```

- Python発展でのみ必須候補として提示する。
- 基本コース完了条件には含めない。
- 2次元周期密度グリッドの自己相関をFFTで計算し、距離方向に平均する実装を採用できる。

## 7. 画面フローと機能要件

### 7.1 全体フロー

```text
ホーム
  → 研究への招待
  → 興味と研究課題
  → 仮説と予想
  → 方法の理解
  → 箱・粒子・snapshot計画
  → Mira計画レビュー
  → 必須の試し計算
  → 比較・計画修正
  → 事前計算済み結果の取得
  → データ品質確認
  → 解析モード選択
  → 解析・リアルタイム作図
  → 結果・解釈・限界
  → ミニ論文
  → Research Constellation・次の問い
```

### 7.2 ステージ別仕様

#### S00 ホーム

表示:

- アプリ名、副題、タグライン
- 「新しい研究を始める」
- 「続きから始める」（保存がある場合）
- 既存プロジェクト一覧
- v0.1テーマカード

要件:

- アカウント登録を要求しない。
- 保存がない場合は「続きから始める」を表示しない。
- 初回にMiraの短い自己紹介を表示する。

#### S01 研究への招待

表示:

- 初期のほぼ一様な分布と現在の網目状分布の模式図
- 「この間に何が起きた？」
- 面白さ、意義、方法、今回のミッション
- クリック可能な用語

学生の選択:

- どこが気になったか
  - 網目模様はどう生まれたか
  - いつ構造が成長したか
  - 高密度領域はなぜ重要か
  - 重力だけでどこまで説明できるか
  - まだわからない

保存:

- `motivationChoice`
- 任意メモ

#### S02 研究課題

学生は、大きな問いを測定可能な問いへ絞る。

必須選択:

- 主研究課題
- 測定対象
- 研究で特に知りたい時間変化または空間スケール

Miraは「測れる量が含まれているか」を確認する。

#### S03 仮説と予想

仮説候補:

- 重力によって密度のむらは成長する
- 宇宙膨張によって分布はより一様になる
- むらの強さはほとんど変わらない
- まだわからない

予想候補は仮説に応じて変えるが、学生に選ばせる。

保存:

- `hypothesis`
- `prediction`
- 任意メモ

Miraは仮説の正誤を判定しない。

#### S04 方法の理解

説明:

- なぜ実観測ではなくシミュレーションを使うか
- N体シミュレーションとは何か
- 一つの計算粒子は一つの素粒子ではないこと
- 周期境界、初期条件、seedの概念
- 暗黒物質のみの計算でできること、できないこと

短い理解確認は知識問題として扱う。

#### S05 研究計画

学生の選択:

- 優先目的: 大きな網目、小さな高密度領域、両方のバランス
- `L`
- `Np`
- snapshot
- 主解析: 密度画像、標準偏差、高密度割合
- 主要図の予想

リアルタイム表示:

- 粒子間隔の目安
- 粒子質量の相対値
- 計算負荷の相対値
- 出力負荷
- 長所と限界

各選択について「選んだ理由」を理由カードから選ぶ。

#### S06 Mira計画レビュー

レビュー状態:

- `research-ready`
- `one-revision-needed`
- `question-method-mismatch`
- `snapshot-insufficient`
- `resource-warning`

レビュー項目:

- 問いと測定量が対応しているか
- 予想と図が対応しているか
- 箱に必要な構造が入るか
- 粒子間隔が目的に合うか
- snapshotで時間発展を判断できるか
- 計算・出力負荷を理解しているか
- 限界を認識しているか

研究実行前に計画をバージョンとして保存する。

#### S07 必須の試し計算

目的:

- 設定の長所と短所を説明だけでなくデータから理解する。

手順:

1. 学生が比較軸を選ぶ。
   - 箱サイズを固定して粒子数を変える
   - 粒子数を固定して箱サイズを変える
2. 結果を見る前に、何が変わるか予想する。
3. 同じ時刻の密度画像と要約統計を横並びで見る。
4. 差を表す選択肢を選ぶ。
5. 元の設定を維持するか変更する。
6. その理由を選ぶ。

比較相手:

- 現在値の隣の候補を提示する。
- 端の値では反対側の隣接値を使う。
- 学生はMiraの提案を変更できる。

表示:

- 同一カラースケールの比較を標準とする。
- 適応カラースケールへ切り替えた場合は明示する。
- 画像だけでなく粒子間隔、相対負荷、`sigma_delta` を併記する。

完了条件:

- 一つ以上の一変数比較を完了する。
- 観察結果を選ぶ。
- 設定維持または修正の理由を保存する。

修正した場合はPlanVersionを追加する。以前のPlanVersionを上書きしない。

#### S08 結果取得

- v0.1ではライブ計算を装わない。
- 「待ち時間を短くするため、同じ条件で事前に計算した結果を読み込みます」と表示する。
- 選択された設定のResultPackageのみ遅延ロードする。
- データ生成元がデモ用fixtureの場合は、常に目立つ場所に表示する。
- 人工的な待ち時間を入れない。

#### S09 データ品質確認

学生は次を確認する。

- 設定が研究計画と一致する
- 必要なsnapshotが存在する
- データが最後まで生成されている
- 欠損値や非有限値がない
- 診断値に重大な警告がない
- 単位、seed、データ版が記録されている

Miraは、確認しないまま解析へ進むことの問題を説明する。

#### S10 解析モード

選択肢:

- **操作で解析**
- **Pythonと一緒に解析**

v0.1では完全自由な「Pythonで解析」は表示しない。両モードは同じAnalysisRecipeを使用し、途中で切り替えられる。

#### S11 解析と図

基本解析:

1. 密度グリッドの読込
2. 平均密度
3. 密度コントラスト
4. ヒストグラム
5. `sigma_delta`
6. 高密度割合（補助）

図:

- 選択snapshotの密度画像
- 初期・中間・現在の密度コントラスト分布
- 宇宙の時間と `sigma_delta` の関係
- 高密度割合の時間変化（選択時）

操作を変更すると、図とキャプション候補をリアルタイム更新する。

#### S12 結果、解釈、結論、限界

四つを別画面または明確な別欄にする。

1. 結果: 図から直接読み取れること
2. 解釈: その理由として考えられること
3. 結論: 研究課題への回答
4. 限界: この研究だけでは分からないこと

Miraは次を検出する。

- 結果にない主張
- 暗黒物質のみの計算からの銀河形成断定
- 一つのseedから宇宙一般へ広げすぎる主張
- 解像度不足の構造に関する断定
- 相関と因果の混同

#### S13 ミニ論文

構成:

1. 題目
2. 背景
3. 研究目的
4. 仮説と予想
5. 方法
6. 試し計算と計画修正
7. 結果
8. 図とキャプション
9. 解釈・考察
10. 結論
11. 限界
12. 次の研究

自動生成するのは文章の骨格のみとする。背景の疑問、解決方法、主要結果、図の説明、解釈、結論、限界、将来展望は学生の選択を必須とする。

出力:

- Markdown
- 印刷用HTML/CSSからブラウザのPDF保存
- 図PNG
- プロジェクトJSON

#### S14 Research Constellation

- 完了した研究を星として表示する。
- v0.1では一つの星だけでも成立するデザインにする。
- 次の研究候補:
  - 解像度を上げると何が変わるか
  - 箱サイズを変えると結果はどれくらい変わるか
  - seedを変えると同じ結論になるか
  - ガスを含めると銀河形成はどう変わるか
  - 暗黒物質の性質が違うと網目は変わるか
- 完了したProjectStateをローカルに保持する。

## 8. 分岐・レビュー規則

### 8.1 計画レビューの最低規則

| 条件 | 状態 | Miraの対応 |
|---|---|---|
| initialまたはz=0がない | snapshot-insufficient | 変化の始点・終点が比較できないことを説明 |
| 中間snapshotが2個未満 | snapshot-insufficient | いつ成長したか判断しにくいと説明 |
| 大規模構造重視でL=25 | one-revision-needed | 小箱の長所と体積不足を説明 |
| 小構造重視でNp=16^3 | one-revision-needed | 粗い粒子間隔を説明 |
| L=100かつNp=16^3 | one-revision-needed | 広いが粗すぎることを説明 |
| L=100かつNp=64^3 | resource-warning | 分解能を保てるが負荷が大きいと説明 |
| 問いが時間変化、図が現在一枚のみ | question-method-mismatch | 問いに対応する時間系列を提案 |
| 条件が整合 | research-ready | 何が整合したかを具体的に説明 |

上表は最小実装であり、Miraコンテンツ側で拡張可能にする。

### 8.2 試し計算後の分岐

- 維持: 理由を保存して本計算へ進む。
- 修正: 新PlanVersionを作成し、再レビューする。
- まだわからない: Miraが差分図の見方を案内し、観察選択へ戻す。

### 8.3 解析後の主張判定

主張カードを次へ分類する。

- `directly-supported`
- `reasonable-interpretation`
- `unsupported`
- `beyond-this-model`

分類をUIに直接見せる必要はないが、Miraの応答と完了ガードに使用する。

## 9. 図と可視化

### 9.1 密度画像

- 2次元投影密度グリッドをCanvasで描画する。
- カラーマップは色覚多様性へ配慮し、rainbowを使用しない。
- 標準はviridisまたはcividis相当とする。
- 同一比較では同じ最小値・最大値を使う。
- 次の表示モードを用意する。
  - 比較モード: 全時刻で固定スケール
  - 構造確認モード: 各時刻で適応スケール
- 現在のモードを図中とキャプションに明記する。
- 数値表を代替表示として提供する。

### 9.2 時間軸

- 初心者向け標準は左から右へ現在に近づく時間順とする。
- 横軸はscale factor `a` を推奨し、hoverまたは用語表示で赤方偏移 `z` を併記する。
- 赤方偏移表示へ切り替えられる場合は、軸方向の違いを説明する。

### 9.3 図の来歴

保存した図は次を持つ。

- figure ID
- タイトル
- 使用snapshot
- AnalysisRecipe版
- 表示モード
- カラースケール
- 作成日時
- キャプション
- 主解析または探索解析の区分

## 10. 解析実装

### 10.1 単一のAnalysisRecipe

操作モードとPythonモードは、同じ意味を持つAnalysisRecipeを使用する。

例:

```json
{
  "schemaVersion": 1,
  "density": {
    "transform": "contrast",
    "smoothing": { "method": "none", "sigmaCells": 0 }
  },
  "histogram": { "bins": 30 },
  "highDensity": { "rhoOverMeanThreshold": 5 },
  "figures": ["density-grid", "delta-histogram", "sigma-growth"]
}
```

### 10.2 JavaScript解析

- 基本コースはブラウザ内のTypeScriptで計算する。
- 非有限値を検出する。
- 同じグリッド、同じ平滑化、同じbin境界を使用する。
- UI操作はdebounceし、操作中に画面を固めない。

### 10.3 Python解析

- Pyodideを遅延ロードする。
- Web Worker内で実行する。
- Core UI、データ、初期bundleにPyodideを含めない。
- Pythonが利用できない場合も基本コースは完了できる。
- Python停止ボタンはWorkerをterminateし、再作成できる。
- NumPyとMatplotlibを基本とする。
- v0.1でphotutils、SEP、Astropyを要求しない。

Python画面:

- Miraの説明
- 編集可能なコード
- 実行
- 停止・再起動
- 標準出力・エラー
- 数値結果
- Matplotlib図
- 操作モードとの比較

### 10.4 数値一致

- JavaScriptとPythonの `mean`, `sigma_delta`, 高密度割合は相対誤差 `1e-6` 以内を目標とする。
- ヒストグラムは同じbin境界を使用し、bin countが一致すること。
- 一致しない場合は完了扱いにせず、開発テストで検出する。

## 11. データ仕様

### 11.1 データ方針

- v0.1は事前計算済みデータを使用する。
- 12通りの `L × Np` の結果をデータ駆動で切り替える。
- 選択されたパッケージのみ遅延ロードする。
- 生の巨大な粒子出力をリポジトリへ置かない。
- 教育用に縮小した投影密度グリッド、要約統計、previewを置く。
- 実データが用意できるまでは、明確にラベル付けしたdemo fixtureを使用できる。
- demo fixtureをCWS計算結果と表示してはならない。

### 11.2 推奨ディレクトリ

```text
public/data/cosmic-web/v1/
├── catalog.json
├── L025_N016/
│   ├── manifest.json
│   ├── snapshots/
│   │   ├── initial.f32
│   │   ├── z10.f32
│   │   ├── z5.f32
│   │   ├── z2.f32
│   │   ├── z1.f32
│   │   └── z0.f32
│   ├── summaries.json
│   └── previews/
└── ...
```

### 11.3 manifest必須項目

```json
{
  "schemaVersion": 1,
  "packageId": "L050_N032_seed0001_v1",
  "dataVersion": "1.0.0",
  "provenance": {
    "kind": "cws",
    "generator": "Cosmic Web Simulator",
    "generatorVersion": "TBD",
    "createdAt": "TBD",
    "notes": ""
  },
  "simulation": {
    "boxSizeMpcOverH": 50,
    "particleSide": 32,
    "particleCount": 32768,
    "seed": 1,
    "zStart": 49,
    "boundary": "periodic",
    "physics": "collisionless-dark-matter-only",
    "cosmology": {}
  },
  "grid": {
    "projection": "xy",
    "width": 128,
    "height": 128,
    "dtype": "float32-le",
    "quantity": "rho_over_mean"
  },
  "snapshots": []
}
```

`provenance.kind` は `cws` または `demo-fixture` とする。

### 11.4 データ検証

ビルド前またはCIで次を検査する。

- catalogから全manifestを解決できる
- ファイルサイズとgrid shapeが一致する
- 値が有限で非負
- `rho_over_mean` の平均が許容範囲内
- snapshot ID、z、aが整合する
- summariesの再計算値が許容誤差内
- package IDが重複しない
- provenanceが空でない

### 11.5 再現性

- seed、設定、データ版、生成元を保存する。
- 固定Lで粒子数を比較するデータは、可能な範囲で対応する初期位相を使用する。
- 箱サイズを変えた比較では同じseedだけで同じ物理領域とは限らないことを説明する。

## 12. 状態管理

### 12.1 ProjectState概略

```ts
interface ProjectState {
  schemaVersion: number;
  projectId: string;
  appVersion: string;
  contentVersion: string;
  createdAt: string;
  updatedAt: string;
  currentStage: ResearchStage;
  themeId: "cosmic-web-growth";
  motivation: ChoiceRecord;
  researchQuestion: ChoiceRecord;
  hypothesis: ChoiceRecord;
  prediction: ChoiceRecord;
  planVersions: PlanVersion[];
  activePlanVersion: number;
  pilot: PilotRecord | null;
  resultPackage: ResultPackageRef | null;
  qualityChecks: QualityCheckRecord[];
  analysisMode: "gui" | "python-assisted";
  analysisRecipe: AnalysisRecipe;
  analysisOutputs: AnalysisOutputRef[];
  figures: FigureRecord[];
  interpretation: InterpretationRecord;
  paper: PaperRecord | null;
  glossaryViewed: string[];
  miraHistory: MiraMessageRecord[];
  completedAt: string | null;
}
```

### 12.2 PlanVersion

各PlanVersionは次を持つ。

- version番号
- 作成日時
- 研究目的
- `L`, `Np`, snapshot
- 主解析
- 選択理由
- 予想
- Miraレビュー
- 前版からの変更理由

### 12.3 自動保存

- 意味のある選択変更後にIndexedDBへ保存する。
- 連続操作はdebounceする。
- 保存状態を画面へ小さく表示する。
- 書込失敗を無視せず、再試行とJSON書出しを案内する。
- 戻る操作で選択を失わない。

### 12.4 スキーマ移行

- `schemaVersion` を必須とする。
- JSON import時に版を検査する。
- 対応する旧版はmigrationする。
- 未対応の新版は上書きせず、読み込めない理由を表示する。

## 17. 完成条件

v0.1は次をすべて満たしたとき完成とする。

1. 天文学知識がない利用者が、必須自由記述なしで完了できる。
2. 研究テーマの面白さと意義が冒頭で伝わる。
3. 問い、仮説、方法、測定量、結果、解釈が記録上つながる。
4. 箱サイズと粒子数の選択が派生量、Mira評価、データへ反映される。
5. 試し計算が必須で、一変数比較と計画維持・修正を経験できる。
6. 修正前後のPlanVersionが残る。
7. snapshot選択が解析可能性へ影響する。
8. 密度画像、ヒストグラム、`sigma_delta` の図を作れる。
9. 比較モードと適応表示の違いを説明する。
10. 結果、解釈、結論、限界を別々に選ぶ。
11. 暗黒物質のみの計算から銀河形成を断定できない。
12. GUIとPythonの主要数値が許容誤差内で一致する。
13. Miraの用語解説と学問リンクが主要画面で動く。

## 付録A. Phase 1Cで承認された仕様校訂

### A.1 大規模構造模式図

S01の比較図は、同じ大きさ・同じ縮尺の領域と同数の決定論的トレーサ粒子を使用する。初期側は振幅の小さい密度ゆらぎを持つほぼ一様な分布、現在側は背景密度場、必要に応じた淡いウォール（シート）、幅と密度勾配を持つ複数の曲線状フィラメント、ノード、ノード付近に多く現れるノット、完全な空ではない複数のボイドを複数レイヤで表す。高密度領域を銀河や銀河団として描かない。矢印は「宇宙の時間発展」とだけ示す。図、キャプション、代替説明には、形態を理解する模式図であり実際のシミュレーション結果や定量図ではないことを明記する。

正式な分類名は「宇宙の大規模構造（コズミック・ウェブ）」「フィラメント」「ノード」「ノット」「ボイド」、必要な場合のみ「ウォール（シート）」とする。ノードは複数のフィラメントが交わる接続点、ノットは宇宙の網目の分類で用いられる高密度領域で多くはノード付近に現れるものとする。分類方法や文献によって両者がほぼ同じ意味で使われる場合があり、常に別階層とは教えない。初出は「ノード（ノット）」とする。分類名として「節」「空洞」は使用しない。

### A.2 日本語技術表記

ユーザ向けUI、Mira、教材、用語解説、図、仕様書では、明示的な辞書により次を正本とする。

- データ、ユーザ、コンピュータ、ブラウザ、サーバ、パラメータ、シミュレータ、メモリ
- スナップショット、乱数シード、放射、関数、電場、磁場、重力場、放射輸送

「データー」「ユーザー」「コンピューター」「ブラウザー」「サーバー」「パラメーター」「シミュレーター」「メモリー」「輻射」「函数」「電界」「磁界」はユーザ向け表示に使用しない。すべての長音を機械的に削除せず、「研究パートナー」「エネルギー」など自然な表記は維持する。コード識別子の `snapshot`、`seed`、`parameter` は変更を要求しない。物理量は量記号を斜体、単位と説明的添字を立体とし、数値と単位の間に空白を置く。

### A.3 S04「方法の理解」

研究計画の前に次の五段階を学ぶ。

1. 観測とシミュレーション：同じ領域を数十億年待って観測できない一方、異なる赤方偏移の観測から過去を調べられる。シミュレーションは物理法則と仮定による時間発展を観測と比較する相補的手段であり、観測の代わりではない。
2. N体シミュレーションと計算粒子：多数の計算粒子の位置と速度を重力で時間発展させる。計算粒子は素粒子、星、銀河一個ではなく、多数の暗黒物質を粗視化した要素である。力学、微分方程式、時間刻み、数値積分と結び付ける。
3. 初期条件と乱数シード：密度ゆらぎ、宇宙論モデル、開始時刻を区別する。乱数シードは物理法則や宇宙論パラメータでなく具体的な実現を変える。一つの実現だけを一般化する限界を示す。
4. 周期境界条件：一方から出た粒子が反対側から入る。人工的な端を避ける計算上の方法で、宇宙が立方体という意味でも、箱より大きな情報を回復する方法でもない。コードネイティブ模式図とテキスト代替を持つ。
5. 暗黒物質のみの範囲：暗黒物質の重力的構造形成と密度分布、フィラメント、ノード、ノット、ボイドの成長を扱う。ガスの圧力・流体運動・冷却・放射、星形成、超新星・活動銀河核フィードバック、磁場、銀河の明るさ・色は直接扱わない。高密度領域はガスが集まりやすい重力場となる可能性があるが、銀河形成は直接確認できない。

理解確認は上記五項目を問う検証可能なデータとし、問題ID、選択肢ID、唯一の正答、もっともらしい誤答、「まだわからない」、理由付きフィードバック、関連用語、関連授業を持つ。誤答は再挑戦でき、「まだわからない」は不利益なくヒントを表示する。得点、ランキング、失敗回数による評価を持たず、仮説を判定しない。全必須問題を理解済みにした場合だけS04を完了する。

ProjectStateは `methodUnderstanding` 専用レコードに `contentId`、問題ごとの最新 `questionId`・`choiceId`・`answeredAt`、`completedAt` を保存する。正誤は保存せず現行コンテンツから純粋関数で評価する。旧版を安全に移行し、未知の将来版は拒否する。S02には関心、S03には研究課題、S04には仮説と予想を要求する一元的なステージガードを用い、`choiceId === "unsure"` も選択済みとする。S04完了後はS05「研究計画」を予告するだけとし、S05以降をPhase 1Cでは実装しない。
